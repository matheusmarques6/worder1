Suíte de testes da IA

O que deve ser testado em cada tela (Agentes, Novo agente, Construtor, Conhecimento, Atividade) e no runtime, com o comportamento esperado e o motivo. No fim, o que não deve virar teste e por quê.

As cinco camadas

Cada linha das tabelas diz em qual camada o teste mora. A regra é testar cada coisa na camada mais barata que consegue provar o que importa.

unit

Regras puras

Funções sem banco nem tela (cálculos, rótulos, derivação do Construtor). Vitest, roda em segundos, entra no CI.

api

Rotas do app

Cada rota com Supabase simulado: organização certa, permissão, formato da resposta, efeito gravado. Vitest.

tela

Tela com API simulada

Playwright sobre o app em modo dev com a API simulada que já existe em scripts/ui-compare. Prova que clicar faz a tela mudar como deve, sem banco.

paridade

App ↔ runtime

Lê o código dos dois lados: toda configuração que o Construtor grava tem que ser lida pelo runtime. É o teste que pega o controle morto de verdade.

e2e

Ponta a ponta

Playwright em e2e/, num projeto Supabase de teste e com o runtime no ar. Poucos testes, só as jornadas que dão dinheiro ou prejuízo.

Decisões de 16/10

As três respostas que definem o comportamento antes dos testes. As duas mudanças de tela estão anotadas para fazer em seguida.

1 · Fechar com alterações não salvas: pede aprovação

“Fechar” no Construtor com alteração pendente pergunta “Sair sem salvar?”. Só sai se o lojista aprovar. Sem alteração pendente, sai direto. Mudança a fazer.

2 · Remover fica como está, com confirmação no WhatsApp

A ferramenta continua como rascunho (vale ao Salvar, Ctrl+Z desfaz). A fonte continua valendo na hora. O número de WhatsApp passa a pedir confirmação antes de remover: “Tem certeza? Este número para de ser atendido pelo agente.” Mudança a fazer.

3 · Prioridade: as jornadas de ponta a ponta

As três jornadas reais (criar e ativar, transferência, lacuna) sobem na ordem, logo depois do teste de paridade. Satisfação continua fora da Atividade enquanto não houver coleta.

O que não deve virar teste

Igualdade de pixel com o protótipoO protótipo roda num iframe mais estreito (2 colunas onde o app tem 3), com fontes e dados de mentira. Como teste, ficaria sempre vermelho por motivo falso. A comparação lado a lado continua como relatório para um olho humano.
As palavras da resposta da IAO modelo não responde igual duas vezes. Testa a estrutura: houve resposta, usou a fonte certa, a revisão rodou, a regra bloqueou. O que entra no prompt é testável. O que o modelo escreve não.
A lista viva da OpenRouterDepende da internet e de terceiro, e muda sem aviso. No teste, a chamada é simulada e o que se prova é o formato e a queda para a lista curta.
Posição das bolinhas do grafoA simulação começa aleatória. Testa quem aparece e quem liga com quem, nunca coordenadas.
Cores, espaçamento e CSS geradoO CSS sai de um script a partir do protótipo. Mudança visual se vê no relatório de comparação. Teste de cor quebra a cada ajuste e não pega bug de comportamento.
Textos de ajuda palavra por palavraCopy muda toda semana e o teste vira trabalho de manutenção. O que se testa é que o texto muda quando a opção muda, e os poucos textos que carregam regra (por exemplo, que pedido de atendente sempre vai para a equipe).
Tempos exatos (toast, 0,8 s, animação)Testes com relógio real ficam instáveis. Onde o tempo é regra, como o agrupamento entre 3 e 60 s, testa o limite com relógio simulado.
Os números da API simulada412 conversas e R$ 18.420 são dados de exemplo. Testar esses valores na tela só prova que a simulação não mudou.
O detector de controle morto como bloqueio do CIEle tem falso positivo: botões que abrem algo fora do painel (Testar, Histórico, Ctrl K, Editar missões). Serve como varredura antes de entregar tela nova. Quem bloqueia o CI é o teste de paridade, que lê o código e não erra assim.
Telas já marcadas para remoçãoEvalView, ReportsView e as rotas antigas estão no inventário de remoção. Testar o que vai sair é trabalho jogado fora. O inventário já prova que nada vivo depende delas.
Itens “Em breve”Instagram e Chat do site: basta provar que não são clicáveis. Comportamento real entra quando existir.
Migrations contra produçãoTeste automático nunca escreve em produção. Migration se valida com os testes de banco num Postgres de teste, com o ensaio que desfaz no fim, e com leitura em produção depois de aplicar, como fizemos.
Regras da Meta (janela de 24h)Na tela é só texto informativo. A regra mora no envio do runtime e já é testada lá.

Ordem sugerida

  1. Paridade de configurações. Um arquivo só, pega a classe inteira de “controle que não faz nada” e roda em segundos no CI.

  2. As três jornadas de ponta a ponta (prioridade da decisão 3): criar e ativar, transferência, lacuna. Precisam de projeto Supabase de teste, número de WhatsApp de teste e runtime de staging.

  3. Rotas que faltam: modelos da OpenRouter, lacuna manual, uso com “transferiu”, resumo e registro da Atividade, criação com modelo e fontes, exportação CSV.

  4. Testes de tela com a API simulada, um arquivo por tela, reaproveitando scripts/ui-compare/mock-api.mjs. Inclui Fechar e a confirmação do WhatsApp.
