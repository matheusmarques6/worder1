Plano de implementação: agentes de IA no runtime e a nova aba IA

Passo a passo · 15 de outubro de 2026 · branch claude/debug-console-error-FWrLE · base: relatório de estado e correlação de telas do mesmo dia
Como ler. O plano tem 8 marcos (M0 a M7) e 34 passos numerados. Cada passo diz o que entra (migration, arquivos, endpoint, módulo do runtime), como testar e o critério de aceite. Os passos de um marco podem andar em paralelo nas três trilhas (runtime Python, API e schema, UI) quando a tabela de dependências permitir. Decisões tomadas para fechar o plano: o runtime Python é o único motor; o legado TypeScript fica só como rollback até o M1 terminar e é apagado no M7; vários agentes por loja ligados a entradas; conhecimento da loja com vínculo por agente; edição inline mantida no editor em órbita.

Princípios e trilhas

  • Nada chega ao cliente sem o Juiz 1. Toda capacidade portada do legado passa pelo guarded_reply. Isso já é regra do runtime e vale para áudio, visão e tools novas.
  • Uma migration por passo, sempre reversível. Migrations em supabase/migrations/ com down comentado; a suíte runtime/tests/db roda contra banco limpo no CI (.github/workflows/runtime.yml). Tabelas hoje fora da cadeia (evals, propostas, integrações) entram na cadeia no M0.
  • Trilhas. RT runtime Python · API Next.js rotas e schema · UI telas. Um passo marcado com duas trilhas tem duas pessoas ou duas sessões.
  • Cada passo fecha com teste. Vitest para TS, pytest (unit, db, pipeline) para o runtime, Playwright para as telas críticas (criar agente, ativar, playground).
  • Commits e push só na branch indicada. Um commit por passo, prefixo feat(ai), feat(runtime), feat(db), feat(ui).
